Firebolt Core is all about high-throughput, low-latency data processing. As outlined in [Connect](/firebolt-core/firebolt-core-connect), all communication with Firebolt Core ultimately occurs through SQL and data processing is no exception. Firebolt Core generally supports the full SQL dialect documented in our [SQL reference](/reference-sql), except a few exceptions that concern features specific to our managed Cloud data warehouse (e.g. RBAC or engine management commands). A complete list of differences between Firebolt Core and the managed Firebolt Cloud data warehouse can be found in [Differences between Firebolt Core and managed Firebolt](/firebolt-core/firebolt-core-differences). 

The remainder of this page focuses specifically on importing, managing, and exporting data in Firebolt Core.

## Importing External Data

External data can be imported into Firebolt Core from different object storage providers.

In the default configuration, you can import data from [Amazon S3](https://aws.amazon.com/s3/) and [Google Cloud Storage](https://cloud.google.com/storage). In addition, Firebolt Core can work with any S3-compatible object store like [MinIO](https://www.min.io/) or [Cloudflare R2](https://www.cloudflare.com/developer-platform/products/r2/). To enable this, you can use the `default_s3_endpoint_override` config property in the [Firebolt Core Configuration File](/firebolt-core/firebolt-core-operation#configuration-file).

* Raw data files in many different formats can be imported directly from object storage.
    * The easiest way to access such data is to import it into a SQL table using [COPY FROM](/reference-sql/commands/data-management/copy-from). `COPY FROM` supports many convenience features such as schema discovery or metadata filtering, and can easily adapt to different data loading workflows.
    * Alternatively, you can also create an [external table](/reference-sql/commands/data-definition/create-external-table) encompassing all relevant data files. This has the advantage that no data is persistently stored and thus duplicated on the Firebolt Core cluster itself, but fewer convenience features are available for external tables than for `COPY FROM`.
    * Data files can also be read directly with the [read_parquet(..)](/reference-sql/functions-reference/table-valued/read_parquet) or [read_csv(..)](/reference-sql/functions-reference/table-valued/read_csv) table-valued functions.
* [Apache Iceberg](https://iceberg.apache.org/) tables can be read through the [read_iceberg(..)](/reference-sql/functions-reference/table-valued/read_iceberg) table-valued function.
    * We currently support a subset of Iceberg catalogs, including file-based catalogs, the Databricks Unity catalog, the AWS Glue catalog, or any other catalog that implements the Iceberg REST Catalog API.
    * The data files of the Iceberg table may be stored in any of the supported object stores.

Note that data stored on [Google Cloud Storage](https://cloud.google.com/storage) can currently only be accessed through the S3 interoperability layer exposed by GCS. In order to access such data from Firebolt Core, you will need to navigate to the "Access keys for your user account" section of the [Interoperability](https://console.cloud.google.com/storage/settings;tab=interoperability) tab in your Cloud Storage settings and generate an access key & secret for your account there. These will then need to be specified as the `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` parameters of the respective SQL command or function (e.g. [CREATE LOCATION](/reference-sql/commands/data-definition/create-location), [CREATE EXTERNAL TABLE](/reference-sql/commands/data-definition/create-external-table), or [read_iceberg(..)](/reference-sql/functions-reference/table-valued/read_iceberg)).

## Managing Metadata & Data

In addition to processing external data, Firebolt Core can also manage relational data itself. Most [DDL](/reference-sql/commands/data-definition) and all [DML](/reference-sql/commands/data-management) commands are supported in Firebolt Core for this purpose.

For production deployments, configure object storage (e.g. [Amazon S3](/firebolt-core/firebolt-core-operation/firebolt-core-object-storage-access/firebolt-core-object-storage-access-s3)) as the backing store for managed table data. With object storage, the authoritative copy of all data resides in the object store, and node volumes serve as a local cache. This provides strong durability guarantees — data survives complete volume loss — and enables cluster resizing without data loss. See [Data durability](/firebolt-core/firebolt-core-operation/firebolt-core-fault-tolerance#data-durability) for a full discussion.

Without object storage, data is stored exclusively on each node's local volume and cannot be shared between clusters. Tables are sharded across all nodes, which means a cluster containing such tables cannot be resized to a different number of nodes without data loss (see also [Differences between Firebolt Core and managed Firebolt](/firebolt-core/firebolt-core-differences)).

## Exporting Data

Data can be exported from Firebolt Core through the following means.

* [COPY TO](/reference-sql/commands/data-management/copy-to) writes raw data files to [Amazon S3](https://aws.amazon.com/s3/) or [Google Cloud Storage](https://cloud.google.com/storage).
* Alternatively, you can also process query results within your client application (see [Connect](/firebolt-core/firebolt-core-connect)). If the only goal is to persist query results to raw data files (e.g. in an ETL pipeline), doing this in the client will generally be slower than using `COPY TO` due to the added cost of serializing and transferring data to the client.

Analogously to reading data, writing data to [Google Cloud Storage](https://cloud.google.com/storage) currently goes through the S3 interoperability layer exposed by GCS and requires a suitable access key & secret ([see above](#importing-external-data) for details).
